# Fase 3.5 — Rehost del stack legacy (lift-and-shift + strangler) — Design

**Date:** 2026-07-18
**Status:** Approved (brainstorming session)
**Depends on:** Phases 0–3 (complete). Deployed: VPC, CI/CD (`deploy-dev.yml`), RDS MariaDB `serfel-dev-db`, Cognito user pool + products HTTP API + new Angular frontend (SST StaticSite). This phase is **additive** — it does not touch the Phase 3 PoC.

---

## 1. Goal & shape

The previous hosting is being decommissioned. The existing legacy applications must run on **AWS as-is** so hosting can be cut over, **without** waiting for the module-by-module serverless rewrite (Fase 4+). This phase **rehosts** the legacy stack next to the new serverless PoC and establishes a **strangler-fig** transition: legacy and new run side by side, and Fase 4+ progressively replaces legacy modules until the legacy apps can be decommissioned.

Legacy apps to migrate (all share the **one** RDS MariaDB already migrated, `serfel-dev-db`):

| App | Today | Target in this phase |
|---|---|---|
| PHP app #1 (5.6) | APIs + some server-rendered pages | **Docker container on ECS Fargate**, as-is |
| PHP app #2 (5.6) | APIs + some server-rendered pages | **Docker container on ECS Fargate**, as-is |
| Node app #1 (Express) | JSON API, HTTP **Basic Auth** | **Lambda** ported to the Phase 3 pattern (Hono, mysql2 pool, ARM64, private subnet) |
| Node app #2 (Express) | JSON API, HTTP **Basic Auth** | **Lambda** ported to the Phase 3 pattern |
| Angular 14 app | SPA, calls the PHP + Node services | **S3 static build** behind CloudFront; **untouched** otherwise |

**No hard deadline** — rehost cleanly, not as a firefight. PHP 5.6 is EOL and painful to rewrite, so it is lifted as-is; the two Express apps are cheap to port to the established Lambda pattern, so they are.

## 2. Target architecture (hybrid / transitional)

This phase changes the plan's target from *pure serverless* (§1 of `plan-trabajo`) to a **hybrid, transitional** architecture. That is the honest end-state during migration:

```
                          ┌─────────────────────────────┐
   Usuario ──HTTPS──────> │  CloudFront (rehost distro)  │
                          └───────────────┬─────────────┘
       /  (SPA)              /api/node/*        /php-app-1/*  /php-app-2/*
          │                       │                    │
          ▼                       ▼                    ▼
   ┌──────────────┐      ┌─────────────────┐   ┌──────────────────┐
   │ S3 (Angular  │      │ API Gateway     │   │ ALB interno       │
   │ 14 legacy)   │      │ HTTP API (node) │   │ (path routing)    │
   └──────────────┘      │ Basic Auth      │   └────────┬─────────┘
                         │ authorizer      │            │
                         └────────┬────────┘   ┌────────▼─────────┐
                                  │            │ ECS Fargate      │
                         ┌────────▼────────┐   │ php-app-1 (5.6)  │
                         │ Lambdas node×2  │   │ php-app-2 (5.6)  │
                         │ (VPC privada)   │   │ (VPC privada)    │
                         └────────┬────────┘   └────────┬─────────┘
                                  │                     │
                                  └──────────┬──────────┘
                                    ┌────────▼────────┐
                                    │ RDS MariaDB      │
                                    │ serfel-dev-db    │
                                    └──────────────────┘

   Coexiste, sin cambios:  Phase 3 PoC → su propio CloudFront + HTTP API (Cognito) → products Lambda → misma RDS
```

**Coexistence is the key property.** The Phase 3 PoC keeps its own CloudFront distribution and its own Cognito-protected HTTP API. The rehost is a **separate** set of resources with its **own** CloudFront. Two frontends (legacy Angular 14, new Angular) and two auth models (Basic Auth for legacy Node, Cognito for new) run in parallel. Nothing in the PoC is rewired. Domain unification (one host fronting both frontends) is deferred to Fase 6 (Route 53 + ACM).

## 3. Front door & routing — **Option A** (single CloudFront, path-based multi-origin)

One CloudFront distribution for the rehost, one origin per concern, so the legacy Angular app calls its backends **same-origin** (no CORS, matching how it behaves today):

| Path pattern | Origin | Notes |
|---|---|---|
| `/*` (default) | S3 (Angular 14 build) | SPA fallback 403/404 → `/index.html` |
| `/api/node/*` | API Gateway HTTP API (node Lambdas) | Basic Auth authorizer; **not cached** (forward `Authorization`) |
| `/Distribuidor/*` | Internal ALB → single Fargate PHP service | **not cached**; forward all headers/cookies/query for PHP sessions |
| `/SerfelWeb/*` | Internal ALB → **same** Fargate PHP service | idem (both apps in one container, §4) |

- The exact legacy base paths must match what the Angular 14 app already calls. If the legacy app uses absolute hostnames per service today, the minimal change is to point them at these same-origin paths (a config/`environment.ts` change), **not** a code rewrite.
- Rejected: **B — subdomains per app** (reintroduces CORS, more Route 53/ACM). **C — everything behind API Gateway** (VPC Link in front of server-rendered PHP adds a hop, 30s timeout and payload limits for no gain).

## 4. PHP on ECS Fargate

> **Corrected against the vendored source (2026-07-21).** `legacy-php/` is ONE Bitbucket repo whose own `docker-compose.yml` builds a **single** `php:5.6-apache` container serving **both** apps from one Apache doc root: `Distribuidor/` (raw PHP, deprecated `mysql_*` API) and `SerfelWeb/` (CodeIgniter). So the rehost is **one Fargate service + one image serving both apps**, not two services. There is already a working `Dockerfile` (`docker-php-ext-install mysql pdo pdo_mysql`, `a2enmod rewrite`) to build from.

- **Image:** build from the vendored `legacy-php/Dockerfile` (base `php:5.6-apache`, extensions `mysql pdo pdo_mysql`, rewrite). The compose file volume-mounts the source for local dev; the **Fargate image must `COPY` both `Distribuidor/` and `SerfelWeb/` into the doc root** instead. One image in **ECR** (`serfel-dev-rehost-php-app-1`; the second repo from Task 2 stays empty/unused — empty ECR repos are free). Pin the digest; PHP 5.6 is EOL.
- **Service:** **one** ECS Fargate service, **1 task** to start (0.25 vCPU / 0.5 GB Fargate floor; bump if needed). Private subnets; Fargate spans AZs automatically.
- **Load balancer:** one **internal ALB**; one target group for the single PHP service. CloudFront routes **both** `/Distribuidor/*` and `/SerfelWeb/*` to it (§3). Health check on a cheap path (add a `health.php`, or an existing 200 route).
- **DB connectivity — repoint via env (decided):** edit `Distribuidor/Coneccion/coneccion.php` (`getUsuarioBD`/`getPassBD`/`getNomBD` + the `mysql_connect` host) and `SerfelWeb/application/config/database.php` to read `getenv('DB_*')`, injected from **Secrets Manager** (`serfel-dev-db-credentials`) → host = RDS endpoint, db = `serfel`, user = `serfeladmin`. Never bake creds into the image.
- **TLS — relaxed for the PHP path (decided):** the legacy `mysql_*` API can't do TLS, but the RDS param group enforces `require_secure_transport=ON`. Relax it for the PHP path (a dedicated non-TLS DB user, or turn the enforcement off) so the apps connect over the private VPC unencrypted. **The Node Lambdas keep TLS to RDS** — only the PHP path is relaxed.
- **Sessions:** PHP session auth kept **as-is**; file-based sessions fine at 1 task. Scaling >1 task later requires a shared session store (carry-forward).
- **No auto-stop:** Fargate tasks are the cost floor of this phase (§9).

## 5. Node Express → Lambda (Phase 3 pattern)

Each Express app becomes **one Lambda per app**, following the exact pattern established by `lambdas/products`:

- **Runtime/shape:** Node 22, ARM64, VPC private subnets, **mysql2 pool declared at module level** (`connectionLimit: 1`), TLS to RDS, internal router (**Hono**) replacing Express routing.
- **Port, don't rewrite:** the HTTP layer (Express `app`, middleware) is dropped; the **business logic inside each handler is ported** with explicit TypeScript types (no `any`), reusing the same mysql2/Drizzle access style. This is a mechanical port, not a domain redesign (that's Fase 4).
- **Auth — Basic Auth authorizer:** a **Lambda authorizer** (REQUEST type) validates the HTTP `Authorization: Basic` header against the same credentials the Express apps use today, so the legacy Angular app is **unchanged**. Credentials live in Secrets Manager, not in code. This is explicitly a **temporary** authorizer; the strangler rewrite swaps these routes to Cognito later (plan §8.4).
- **Routing:** ported Lambdas sit on an HTTP API under `/api/node/*`. This can be the **same** HTTP API as the products PoC (per-route authorizers: Cognito on products routes, Basic Auth on node routes) or a **separate** HTTP API — either works; separate API is cleaner for a clean teardown when these modules are stranglered. **Decision: separate HTTP API** for the rehost, so legacy and new have independent lifecycles.
- **Shared types:** DTOs/Zod for the ported endpoints go in `packages/shared` alongside the Phase 3 types, so they're reusable when Fase 4 redesigns these domains.

## 6. Networking

- All compute stays **inside the existing VPC**, private subnets, reaching `serfel-dev-db` over the existing security-group path (add SG rules for the Fargate tasks and the new Lambdas, mirroring the products Lambda's access).
- **CloudFront → ALB:** the ALB is **internal**. CloudFront reaches it either via **VPC origins** (CloudFront native private origin) or by keeping the ALB internet-facing but locked to CloudFront (WAF + a shared secret header / prefix-list). **Decision: internal ALB + CloudFront VPC origin** to avoid exposing the ALB publicly; if VPC-origin support is a problem in the region/SST version, fall back to an internet-facing ALB restricted to CloudFront's managed prefix list + a secret header validated at the ALB.
- **NAT/egress:** Fargate tasks pulling from ECR and reading Secrets Manager use the existing NAT or **VPC endpoints** (ECR, Secrets Manager, S3 gateway) — prefer endpoints to keep NAT cost down (consistent with plan §5 cost notes).
- Encryption in transit (HTTPS at CloudFront; TLS to RDS **for the Node Lambdas**) and at rest (KMS on RDS, already on). **Exception:** the PHP path connects to RDS **without** TLS (legacy `mysql_*` limitation, §4) — mitigated by staying inside the private VPC.

## 7. IaC & repo structure

Everything is defined in the existing **SST v3** app (`serfel/`), deployed to `dev` via the existing `deploy-dev.yml`, so the rehost is reproducible and portable to the client's prod account (plan §Fase 6) like the rest.

```
serfel/                        ← the one repo (GitHub), one SST app
├── apps/
│   ├── frontend/            ← new Angular (Phase 3, untouched, in pnpm workspace)
│   └── legacy-frontend/     ← Angular 14 source, vendored, OUT of the workspace
├── lambdas/
│   ├── products/            ← Phase 3, untouched
│   ├── node-app-1/          ← ported Express app #1 (Hono) — in workspace
│   ├── node-app-2/          ← ported Express app #2 (Hono) — in workspace
│   └── basic-auth-authorizer/  ← shared Basic Auth Lambda authorizer
├── legacy-php/              ← ONE Bitbucket repo (both PHP apps), vendored, OUT of workspace
│   ├── <app-1-subdir>/      ← Dockerfile + app code (subdir name = upstream layout)
│   └── <app-2-subdir>/      ← Dockerfile + app code
├── packages/shared/         ← + DTOs/Zod for ported node endpoints
└── infra/rehost/            ← rehost stack: ECR, Fargate services, ALB, rehost CloudFront, node HTTP API + authorizer
```

- New SST/CDK constructs: `Cluster` + `Service` (Fargate) per PHP app, ALB + target groups, ECR repos, a rehost `Router`/CloudFront with the §3 origins, the node HTTP API + Basic Auth authorizer, ported node Lambdas.
- Resource names parameterized by **stage** (`serfel-<stage>-rehost-*`) — same carry-forward discipline as Phase 3 before the move to the client account.

**Source vendoring (decided 2026-07-19).** Legacy apps are **frozen / bugfix-only** and live in **Bitbucket** while this monorepo is on **GitHub**. `git subtree` is provider-agnostic (operates on git URLs; the merge is local, then pushed to GitHub — Bitbucket is only read), so cross-provider is a non-issue. All legacy source is **vendored into the monorepo** so one `sst deploy` / one CI pipeline builds everything reproducibly (required for the move to the client's prod account, §Fase 6). After each app is live and smoke-passes on AWS, **archive its Bitbucket repo read-only.**

- **The 2 PHP apps share ONE Bitbucket repo** → a **single** `git subtree add --prefix=legacy-php <bitbucket-url> main --squash` brings **both** apps in at once. Their subdirectory names mirror the upstream layout (`legacy-php/<app-1-subdir>`, `legacy-php/<app-2-subdir>`), and the two apps may **share code** in that repo — so each app's **Docker build context** may need to be the shared `legacy-php/` root (with per-app Dockerfiles) rather than an isolated subdir. Confirm the internal layout on import (§12).
- **The 2 Node apps** are each their own Bitbucket repo → subtree each in, then **port** to `lambdas/node-app-N` (drop Express; they *join* the pnpm workspace as TS Lambdas — this is the whole point of the monorepo).
- **The Angular 14 app** (its own Bitbucket repo) → subtree into `apps/legacy-frontend`.
- **Workspace exclusion:** `pnpm-workspace.yaml` must **not** glob `legacy-php/**` (no Node) or `apps/legacy-frontend` (Angular 14 deps collide with the workspace's Angular 18/pnpm). They keep their **own** toolchains/lockfiles: PHP is a pure Docker context; the legacy Angular `StaticSite` build runs its **own** `npm ci && ng build` inside its dir, un-hoisted. The absorbed Node Lambdas **do** join the workspace.
- **`--squash`** on every subtree add: import a snapshot, not the foreign history. Running the `git subtree` commands is a **human step** (needs Bitbucket credentials).

## 8. Testing & cutover

- **PHP:** smoke each app's key endpoints and one server-rendered page against `dev` (login/session flow + a DB-backed read/write). Add a `scripts/rehost-smoke.sh` analogous to `scripts/api-smoke.sh`.
- **Node Lambdas:** unit tests (Vitest) for the ported business logic; integration smoke against `dev` with a Basic Auth header (valid → 200, missing/wrong → 401).
- **Legacy Angular:** point its service base URLs at the same-origin rehost paths; manual browser smoke (it's untouched otherwise, so a config change + click-through is enough).
- **Cutover (no deadline, so staged):** stand the rehost up in `dev`, verify every app end-to-end against the migrated DB, then repeat in the client prod account (Fase 6) and switch DNS. Old hosting is decommissioned **only** after all five apps pass smoke on AWS.

## 9. Cost impact

The rehost adds always-on compute that the pure-serverless plan didn't have:

| Added component | Approx. monthly (us-east-1) |
|---|---|
| ALB (internal) | ~USD 16 + LCU |
| 2× Fargate task (0.25 vCPU / 0.5 GB, always on) | ~USD 18–20 |
| Rehost CloudFront + S3 (legacy Angular) | ~USD 1–5 |
| Node Lambdas + node HTTP API | ~USD 0–1 (within free tier at this scale) |
| **Added total** | **~USD 35–42/mo** on top of the ~USD 18–35 baseline |

- This is the price of keeping PHP 5.6 alive. It **shrinks** as the strangler rewrite (Fase 4+) retires PHP apps: each PHP app decommissioned removes a Fargate service; when both are gone, the ALB goes too, and the architecture collapses back toward the pure-serverless target.
- Cost-reduction levers if needed: run both PHP apps in **one** Fargate service (path routing inside one task) to halve task cost; or a single small EC2 instead of Fargate+ALB (rejected earlier for reproducibility, but revisit if cost matters more than ops-cleanliness).

## 10. Scope

**In scope:** rehost the 5 legacy apps to `dev` (PHP→Fargate, Node→Lambda, Angular 14→S3/CloudFront), Basic Auth authorizer, rehost CloudFront/ALB/ECR, same-origin routing, SG/networking to RDS, smoke tests, cost notes, IaC in the existing SST app.

**Out of scope:** rewriting PHP business logic (that's the strangler, Fase 4+); migrating legacy auth to Cognito; WAF/X-Ray hardening (Fase 5); prod account (Fase 6); redesigning the ported Node domains; moving PHP sessions to a shared store (only if scaled >1 task later).

---

## 11. Strangler path (how this ends)

1. Rehost (this phase) — everything runs on AWS, old host retired.
2. Fase 4 continues building new serverless modules (Cognito, redesigned domains) that **replace** legacy endpoints one at a time.
3. As each legacy module is replaced, remove its route from the rehost CloudFront / retire its PHP service or node Lambda.
4. When the last PHP app is gone, drop the ALB and the legacy Angular app; the new Angular frontend + Cognito + serverless is the sole surviving stack — the original plan's pure-serverless target.
