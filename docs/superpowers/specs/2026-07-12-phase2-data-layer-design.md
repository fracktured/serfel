# Phase 2 — Data Layer (RDS MariaDB + Drizzle)

**Date:** 2026-07-12
**Project:** Serfel — App web de ventas (POC)
**Scope:** RDS MariaDB provisioning, legacy schema introspection into Drizzle, migration Lambda, SSM bastion, real-data import
**Estimated setup time:** 3–5 days
**Depends on:** Phase 1 (VPC with private subnets, `sg-rds`/`sg-lambda`, VPC endpoints, CI/CD via OIDC)

---

## Context

Phase 1 delivered a VPC with private subnets (no NAT, AWS access via VPC endpoints), security groups pre-defined for RDS and Lambda, and a GitHub Actions pipeline. Phase 2 adds the data layer: a private RDS MariaDB instance whose schema is **introspected as-is from the legacy PHP application's database** (provided as a SQL dump), versioned through Drizzle migrations from day one, and seeded with the real data from that dump.

Key decisions made during brainstorming:

| Decision | Choice |
|----------|--------|
| Schema source | Introspect legacy dump as-is (no redesign) — keeps eventual production data migration trivial |
| Legacy access | SQL dump file, loaded into local Docker MariaDB for introspection |
| Reaching the private DB | Migration Lambda (CI/CLI) + on-demand EC2 SSM bastion for ad-hoc SQL |
| Secret rotation | Deferred to Phase 5; Secrets Manager without auto-rotation for now |
| DB uptime | Manual start/stop (infrequent use) + guard against AWS's 7-day auto-restart |
| Seed data | Real data imported from the legacy dump (data-only import through the bastion tunnel) |
| Import flow | Drizzle-first: migration `0000_initial` creates the schema; data imported separately |

**Region:** `us-east-1` · **SST stage:** `dev` only
**Budget impact:** ~$13–15/mo with DB running; ~$2–3/mo stopped (storage + backups); bastion ≈ $0 stopped

## Design

### 1. RDS Instance (`infra/database.ts`)

New SST/Pulumi module, imported in `sst.config.ts` after `vpc`.

- **Engine:** MariaDB **11.4** (latest LTS on RDS)
- **Instance:** `db.t4g.micro` (ARM/Graviton), **Single-AZ**
- **Storage:** 20 GB **gp3**, encrypted at rest (default KMS key), storage autoscaling up to 50 GB
- **Network:** DB subnet group over `private-1a` + `private-1b`; `publiclyAccessible: false`; security group `sg-rds` (from Phase 1)
- **TLS:** parameter group with `require_secure_transport = ON`; CA `rds-ca-rsa2048-g1`
- **Backups:** automated, **7-day retention**, point-in-time recovery enabled
- **Deletion protection:** off in dev (consistent with `removal: "remove"`); on when prod stage is added
- **Exports:** `dbInstanceId`, `dbEndpoint`, `dbSecretArn` for later stacks

### 2. Credentials (Secrets Manager)

- Master password generated by IaC (never in code or state outputs in plain form) and stored in **Secrets Manager** as a standard RDS-style secret: `{ host, port, username, password, dbname }`
- Consumers (migration Lambda now, domain Lambdas in Phase 3) read it at runtime through the existing `secretsmanager` VPC interface endpoint
- **No automatic rotation in this phase.** Rotation (AWS rotation Lambda + graceful re-fetch in consumers) is a Phase 5 hardening item, added once real consumers exist to validate rotation behavior against

### 3. Bastion (`infra/bastion.ts`)

On-demand jump host for SQL clients and the one-time data import.

- **EC2 `t4g.nano`**, Amazon Linux 2023 (SSM agent preinstalled), in a **public subnet** with a public IP — the SSM agent needs to reach the SSM service, and with no NAT Gateway the alternatives are 3 extra paid interface endpoints (`ssm` alone is not enough for Session Manager; it also needs `ssmmessages` + `ec2messages`) or this. Public IP + zero inbound ports is the cheaper, equally safe option
- **No SSH key pair. No inbound rules at all.** Access is exclusively `aws ssm start-session` with document `AWS-StartPortForwardingSessionToRemoteHost` targeting the RDS endpoint on 3306
- Bastion SG: egress 443 (SSM channel) + egress 3306 to `sg-rds`; `sg-rds` gains a second ingress rule allowing 3306 from the bastion SG
- IAM instance profile with `AmazonSSMManagedInstanceCore` only
- **Default state: stopped.** Started on demand via helper script

### 4. Lifecycle Helpers & 7-Day Guard

Root `package.json` scripts wrapping the AWS CLI:

| Script | Action |
|--------|--------|
| `pnpm db:start` / `pnpm db:stop` | Start/stop the RDS instance |
| `pnpm bastion:start` / `pnpm bastion:stop` | Start/stop the bastion EC2 |
| `pnpm db:tunnel` | SSM port-forward: `localhost:3306` → RDS endpoint (starts session; requires bastion running) |
| `pnpm db:migrate` | Invoke the migration Lambda and print its report |

**7-day guard:** AWS auto-restarts a stopped RDS instance after 7 days. An EventBridge rule matching RDS event **`RDS-EVENT-0154`** ("instance started because it exceeded the maximum allowed time being stopped") triggers a tiny Lambda that immediately stops the instance again. The guard only reacts to that specific event — manual starts are untouched.

### 5. `packages/db` (Drizzle)

The placeholder package gets its real content:

```
packages/db/
├── docker-compose.yml       ← local MariaDB 11.4 for introspection & local dev
├── drizzle.config.ts
├── migrations/              ← SQL journal, starting at 0000_initial
├── src/
│   ├── schema.ts            ← introspected from legacy dump, committed
│   └── client.ts            ← createDb() factory (drizzle-orm/mysql2)
└── package.json
```

- **`client.ts`:** `createDb(secret)` returns a Drizzle instance over a `mysql2` pool with `connectionLimit: 1`, TLS enabled. Designed to be instantiated at module level in Lambdas (outside the handler) so warm invocations reuse the connection
- Types export to `@serfel/shared` consumers in Phase 3

**One-time introspection workflow (local):**

1. `docker compose up` MariaDB 11.4 in `packages/db`
2. Load the **schema-only** portion of the legacy dump (`mysqldump --no-data` output, or filtered)
3. `drizzle-kit introspect` → generates `schema.ts`; review and commit
4. `drizzle-kit generate` → produces `migrations/0000_initial.sql`; commit

The legacy dump contains real customer data and is **never committed** — it lives outside the repo, and `*.sql` dumps get a defensive `.gitignore` entry in `packages/db`.

### 6. Migration Lambda (`lambdas/migrate/`)

- **Runtime:** Node 22, ARM, inside the VPC (private subnets, `sg-lambda`)
- Bundles the `packages/db` migration journal; reads DB credentials from Secrets Manager at invocation
- Runs Drizzle's `migrate()` — idempotent by design (journal table tracks applied migrations); response reports which migrations were applied vs. skipped
- **Invocation paths:**
  - Manual: `pnpm db:migrate` (`aws lambda invoke`)
  - CI: a step in `deploy-dev.yml` after `sst deploy`, which first checks the DB instance status via AWS CLI and **skips with a visible warning if the DB is stopped** (given the manual start/stop policy, a stopped DB must not fail the deploy)

### 7. Data Import (One-Time, Manual)

1. `pnpm db:start`, wait for `available`; `pnpm bastion:start` + `pnpm db:tunnel`
2. Migration Lambda has applied `0000_initial` → schema exists, empty
3. Import the **data-only** dump (`mysqldump --no-create-info` from legacy) through the tunnel: `mysql -h 127.0.0.1 -P 3306 ... < dump-data-only.sql`
4. Verify row counts per table against the legacy database

This doubles as a dry run of the eventual production data migration (Phase 6).

### 8. Error Handling Notes

- **Import failures mid-file:** re-runnable by dropping/recreating the database (`DROP DATABASE; CREATE DATABASE;` + re-run migration Lambda) — cheap while dev has no other data
- **Migration Lambda timeout:** 60 s timeout is ample for DDL; if a future migration needs more, raise per-invocation, not globally
- **Introspection mismatches:** MariaDB types Drizzle can't map cleanly (e.g., legacy `ENUM`s, zero-dates) are resolved in `schema.ts` review before committing — the review step is mandatory, not a formality

## Success Criteria

- [ ] `npx sst deploy --stage dev` creates RDS instance, secret, bastion, migration Lambda, and 7-day guard without errors
- [ ] RDS has no public endpoint; connection attempt from the internet fails
- [ ] Migration Lambda applies `0000_initial` on the empty DB; a second invocation reports no-op (idempotent)
- [ ] Data-only import through the SSM tunnel completes; row counts match the legacy dump
- [ ] SQL client on the laptop reaches the DB via `pnpm db:tunnel`
- [ ] `pnpm db:stop` stops the instance; EventBridge guard rule for `RDS-EVENT-0154` exists and targets the stop Lambda
- [ ] A scratch script using `createDb()` runs one typed Drizzle query and returns real imported rows
- [ ] CI deploy succeeds with the DB stopped (migration step skips with warning) and with it running (migration step executes)
